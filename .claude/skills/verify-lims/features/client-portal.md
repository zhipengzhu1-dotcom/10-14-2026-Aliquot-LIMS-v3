# Client portal

A separate sign-in at `/portal/` where a client's contacts follow their own samples, download issued CoAs, submit samples and message the lab. Each contact only sees their own company's records. Code: `public/portal/portal.js` (hash routes), server `server/routes/portal.js`, staff side `public/js/views/portal-inbox.js`.

## Sub-features

- Sign-in card: form `#signin` with `input[name=email]`, `input[name=password]` and `#signin button[type=submit]` "Sign in". Below it is one demo button per contact: `button[data-demo="customer@example.com"]` (Dr. Laura Chen, Acme), `felix.romero@bluestone-bio.example` (Bluestone) and `hannah.schultz@northwind-tx.example` (Northwind). A first sign-in with a temporary password lands on form `#pw` "Choose your password".
- Samples: `#/samples?tab=open|reported|all|shipments`, detail at `#/samples/<id>`, CoA at `#/coa/<id>`. A submission's detail is `#/submissions/<id>`.
- Submit samples (`#/submit`, "Tell us what is coming") is the submission desk: the conversation with the assistant (`.as-chat-col`) beside the draft it fills (`.as-draft-col`). Below 900 px wide only one shows, switched by `.as-tabs button[data-tab=chat|draft]` ("Conversation" / "Submission" with a count of what still blocks sending in `.as-count`). The desk keeps its conversation and draft while the client moves around the portal and starts fresh after sending.
  - Conversation: `textarea#as-message` with `.js-composer button[type=submit]` "Send message" (Ctrl/Cmd+Enter sends), `.as-chat-col button.js-paste` "Attach spreadsheet" (it opens the file chooser; drive it with `agent-browser upload input.js-file <file>`: the sheet's columns are guessed and its rows go straight into the draft table marked from sheet, with a toast "N samples added from <file>"; there is no preview or mapping panel, columns with no place stay as extra detail on a line under their row), and the picker `select.js-pick` ("Opus 5.5 · low effort"; values `<model>|<effort>` from the `MODELS` x `EFFORTS` table) that picks the model and effort for this conversation. Replies are `.msg.lab.as-reply`; their meta `.js-answered-by` reads "<model that answered> · <effort> effort · <seconds> s", plus "· N tries" after a retry. The model's questions show as `button.as-choice[data-answer]`; a click sends that option as the client's answer. A value marked you edited is never changed by the model: when a reply changes it, the server keeps the client's value and asks instead ("You set the courier to \"DHL\". Change it to \"UPS\"?" with chips "UPS" and "Keep what I set"; "You set … Clear it?" with the chip "Clear it" when the reply empties it; "You emptied <field>. Set it to \"…\"?" when the client had emptied it; long values show a 40-character chip and the full value in the question). Those two chips act in the browser without another model turn: the first sets the value ("you edited"), "Keep what I set" is remembered so the same proposal for that field is not asked again in this conversation. When the next reply arrives, unanswered proposal chips of earlier turns are disabled with `.as-retired` "Replaced by the newer reply.", and the new reply asks again any that still apply; a proposal chip whose sample is gone from the draft does nothing and reads "That sample is no longer in the draft." A proposed value that reads "Keep what I set" gets the chip "Change it". Every sample row carries an id (`r1`, `r2`, never sent to the lab), taken from the draft's `next_row` counter that the browser and the server only count up, so an id is never given twice in a conversation, even after the client removes its row; rows are matched by id, so a reply that inserts, reorders or drops rows never moves an edited value onto another row, and an edited row the reply left out stays, with a question. While a turn runs `.as-typing` shows, with the reply's words so far in `.js-partial` ahead of it as the server streams them, the chips are disabled, the draft stays editable but its rows are fixed (`button[data-add]` and `button[data-remove]` disabled, attaching a spreadsheet toasts that the assistant is drafting), Send to lab is blocked with "the assistant is still drafting", and every field the client changes in that time keeps the client's value and "you edited" over the reply. A turn lasts as long as the stand-in's `delay_ms` plus its stream pauses (see [submission-assistant.md](submission-assistant.md)); wait on `!document.querySelector(".as-typing")`, never a fixed time. When a turn is refused (a 503 such as the assistant being off or Claude unreachable, or a 400 such as a message over 20000 characters), the conversation gets a system note `.msg.system` "<the server's message> You can keep filling in the submission by hand." and the draft stays as it was.
  - Assistant off: the chat column shows `.as-off` "The assistant is off." ("Your lab has not turned it on."); only when `GET /api/portal/assistant` itself fails does it read "The assistant could not be reached.". The page subtitle then reads "Fill in what you are sending. Only the sample names are required." At 900 px and wider both columns still show, the chat column holding only that notice; below 900 px the desk opens on the Submission tab, so the draft is the whole page.
  - Draft: the form (`.as-form`) is the samples table and nothing else (no ledger card, no shipment fields, no test chips); the browser drops whatever the assistant drafts for the rest of the submission and any question about it, so a draft carries only samples and the default turnaround. Every field is `[data-field=<path>]` (`samples.0.batch_no`) holding an input or select with id `d-<path with dashes>` (e.g. `#d-samples-0-description`) and `data-path`; its tag `.ptag` reads from you, from sheet, guessed (dashed amber), fixed (blue), default, you edited, or needs you (orange). A gate problem on a sample is shown on its cell (`p-ask`, its message in the cell's title) and in the send bar. Samples show as a table at 560 px of draft width and up (so at 1280 and 1440 wide, with the draft column about 605 px), cards below, switching on resize even while a draft field has focus (focus and caret are kept); the table leads with # and Sample description, which stay pinned while the other columns scroll sideways inside `.as-tbl`; `button[data-add]` "Add a sample", `button[data-remove]`. The draft has no spreadsheet button of its own; spreadsheets come in through the conversation's "Attach spreadsheet" (see above).
  - Every edit runs `POST /api/portal/submissions/check`. The send bar `.as-send` says what still blocks: every gate problem's message, then "checking your changes" while a check runs and "the assistant is still drafting" during a turn; guesses are only counted (`blockers` in `portal.js`). `button.js-send` "Send to lab" stays disabled until nothing blocks, sends once through `POST /api/portal/submissions`, and goes to the confirmation below.
  - The server checks every submission through one gate, `SUBMISSION_GATE` in `server/submission-gate.js`. `POST /api/portal/submissions/check` runs it on a body without saving and returns `{ ok, problems: [{ path, rule, message, fix? }] }`, every problem at its path (`storage`, `samples.<index>.stage`, `method_ids`); `fix.value` is set when the gate knows the value meant (an option differing only in case, spaces or dashes; the tests list without the ones the client cannot order). `POST /api/portal/submissions` refuses with the first problem's message.
- Submission assistant (admin switch, `/api/settings/assistant` and `/api/portal/assistant`, the `claude` limits, and how to drive it on the stand-in Claude): see [submission-assistant.md](submission-assistant.md).
- Confirmation: after sending, the portal goes to `#/submissions/<id>?sent=1`. While the submission is open, that page shows `.label-card` with the number in `.label-card .big` and the buttons `.js-copy` "Copy number" and `.js-print` "Print"; a "What happens next" card with the status pill and `ol.timeline`; and the links "Your shipments" and "Send another". Without `?sent=1`, or once the submission is closed, the same route shows a normal page head with the code as `h1` and a "Conversation" link.
- Timeline (`SUBMISSION_STEPS`): "Sent to the lab" → "Lab is expecting it" → "Box received". It ends at Received; after that each sample has its own progress, linked under "Logged as S-…". A Declined or Withdrawn submission stops after its last reached step, with an extra `li.stop` row. The `SUBMISSION` table gives each status its pill: Submitted "Sent to lab", Acknowledged "Expected", Received "Received", Declined "Declined", Withdrawn "Withdrawn". Look for "Expected" on screen and `Acknowledged` in the API.
- Withdraw a submission: while `can.withdraw` is true (`GET /api/portal/submissions/<id>` → `can`; true while Submitted), the status card shows "Sent by mistake? Withdraw SUB-…. Available until the lab confirms.", where "Withdraw SUB-…" is the link-button `.js-withdraw`. Toast "Submission withdrawn"; the pill becomes Withdrawn, the timeline ends with "You withdrew this shipment…", and the line goes.
- Requests for method development, validation, transfer or other work: `#/requests`, new at `#/requests/new` (form `#request`, "Send request"). The client's request detail is read-only. The lab moves a request only forward: Submitted → Under review → Proposal sent → Accepted (a proposal can also go straight from Submitted), or Declined while open; Accept only from Proposal sent, and a response that keeps the status is a reply.
- Messages:
  - `#/messages` lists threads.
  - "New" (`.threads-card a[href="#/messages/new"]`; the bare selector matches more than one link) opens form `#newthread` with `input[name=subject]`, `select[name=sample_id]` and `textarea[name=body]`, then "Send".
  - Reply with form `#reply` and its `textarea[name=body]`. Cmd/Ctrl+Enter sends.
- Account (`#/account`, which also has its own `button.js-out` "Sign out") and sign-out: `button.avatar.js-me`, then `button.js-signout`.

## How to get to it (user POV)

- Open `<base>/portal/` and sign in as a client contact.
- Navigate with the top nav: `.nav a[data-nav=overview|samples|submit|requests|messages]`. Below desktop width `.nav` is hidden; use `nav.tabbar a[data-nav=…]` instead.
- Staff see the other side under **Client portal** in the sidebar (`/portal-inbox`). It opens on Messages. Submissions are at `/portal-inbox?tab=submissions` (open ones by default), and a submission's detail is at `/portal-inbox/submissions/<id>`, with Acknowledge, Decline and "Receive samples" (`button[data-act=receive]`) offered from its `can` flags. Acknowledge and Decline need `portal.respond` (manager, QA, scientist, business); Receive needs `samples.receive` (admin, manager, scientist, analyst). On an open submission priya.raman sees all three, tom.fletcher only Receive, and grace.holloway and daniel.okafor get `can.receive: false`, so no "Receive samples". Requests are at `/portal-inbox?tab=requests` and `/portal-inbox/requests/<id>`.

## Driving it with agent-browser

Before merging a change that touches the portal, run the portal browser tests: `node --test test/portal-send.test.js test/portal-edge-cases.test.js` (they skip without agent-browser, so CI does not run them).

Run the viewport and reduced-motion setup from SKILL.md first. Without it the splash covers the nav in the new tab and the drive fails.

```bash
agent-browser open "$B/portal/"
agent-browser wait --fn '!document.getElementById("splash")'   # the splash can cover the demo buttons after they render
agent-browser wait '[data-demo="customer@example.com"]'
agent-browser scrollintoview '[data-demo="customer@example.com"]'
agent-browser click '[data-demo="customer@example.com"]'
agent-browser wait 'header.top nav.nav a[data-nav]'
agent-browser tab new "$B/portal/#/"                           # clicks stop landing in the sign-in tab (see Gotchas)
agent-browser wait --fn '!document.getElementById("splash")'
agent-browser wait 'header.top nav.nav a[data-nav]'
agent-browser click '.nav a[data-nav=submit]'
agent-browser wait '#d-samples-0-description'
agent-browser fill '#d-samples-0-description' 'Portal verification sample'
agent-browser wait --fn '!document.querySelector("button.js-send").disabled'
agent-browser click 'button.js-send'                           # "Send to lab"
agent-browser wait '.label-card .big'                          # "SUB-YYYY-NNNN"
agent-browser eval 'location.hash'                             # "#/submissions/<id>?sent=1"
```

End state that proves it:

- **Screen:** `#/submissions/<id>?sent=1` with the code in `.label-card .big`, the pill "Sent to lab", "Sent to the lab" as the current timeline step, the Withdraw line, and the links "Your shipments" and "Send another".
- **API:** as a staff user, `GET /api/portal-admin/submissions` lists the new code with status `Submitted`, and `GET /api/portal-admin/threads` has an automatic thread "Sample submission SUB-…".
- **Messages:** after sending, the new `.msg.client .bubble` appears in `#msgs`. The staff badge is `[data-badge=portal]` in the sidebar, the same number as `GET /api/nav` → `portal`. It counts Submitted submissions, Submitted method requests, and threads with unread client messages. A new submission without notes adds 1, because its automatic thread holds only a system event; with notes it adds 2, because the notes are posted as a client message. A new client thread adds 1. Withdrawing takes the submission's 1 off again.
- **Isolation:** a contact from another company (e.g. `felix.romero@bluestone-bio.example`) must not see Acme's records. Under Felix's portal session:
  - GET `/api/portal/samples/<acme id>`, `/samples/<id>/coa`, `/threads/<id>`, `/submissions/<id>` and `/requests/<id>` return 404, and so do POST `/threads/<id>/messages` and POST `/submissions/<id>/withdraw`.
  - His lists hold only Bluestone's rows, and some are empty in the seed: `/api/portal/samples` defaults to open samples and returns `[]`, while `?status=all` returns his 3 samples; `/api/portal/submissions` may be empty. Check that no list contains Acme codes or subjects.
- **Withdraw:** the API then returns `status: "Withdrawn"` and `can.withdraw: false`; the staff list `GET /api/portal-admin/submissions?status=Withdrawn` holds it and the default open list does not; the audit has `STATUS` on `portal_submissions` "Withdrawn by the client". A second withdraw returns 400 ("This submission is withdrawn — contact the laboratory to change it").

## Gotchas

- **Behavior** (`server/portal-auth.js`). The portal uses its own cookie and session, separate from the staff app's. Signing in to one does not sign in to the other.
- **Behavior** (`portal.js`). The nav links render twice (desktop `.nav` and mobile `nav.tabbar`). Scope selectors to `.nav` on desktop and to `nav.tabbar` at phone width.
- **Harness quirk** (`.send-bar` is `position: sticky; bottom: 0` in `portal.css`, and agent-browser refuses a covered click). On desktop the sticky `.send-bar` can cover buttons in the draft, and agent-browser refuses the click. Scroll the button into view first.
- **Behavior** (`portal.js`). The send bar re-renders after every check. Wait on the `disabled` state of `button.js-send`, not a fixed time.
- **Harness quirk** (`portal.js` calls `confirm()`, which agent-browser cannot answer). "Withdraw" on a submission (`.js-withdraw`) calls native `confirm()`, which blocks automation. Before clicking, run `agent-browser eval 'window.confirm=()=>true'`.
- **Behavior** (`portal.js`). Portal toasts are a single `.toast` element, not the Staff app's `.toasts`: `agent-browser eval 'document.querySelector(".toast")?.textContent'`.
- **Behavior** (`portal.js`, `boot.js`). The portal shows a splash and an `.arrive` animation, plus skeleton loaders after about 160 ms. Wait for content selectors, not fixed times.
- **Harness quirk** (`scripts/api.mjs` only knows the staff login). `scripts/api.mjs` signs in through the staff login only. For portal API reads, sign in yourself and keep the jar in the run folder so cleanup removes it:
  ```bash
  curl -s -c .verify/runs/verify/portal-acme.jar -H 'X-Requested-With: aliquot' -H 'Content-Type: application/json' \
    -d '{"email":"customer@example.com","password":"demo1234"}' "$B/api/portal/login"
  curl -s -b .verify/runs/verify/portal-acme.jar "$B/api/portal/submissions"
  ```
  Every non-GET needs `X-Requested-With: aliquot`, or the server answers 403. A portal cookie gets 401 on staff endpoints.
- **Hypothesis** (cause unknown, app or harness; tracked in [issue #11](https://github.com/zhipengzhu1-dotcom/10-14-2026-Aliquot-LIMS-v3/issues/11)). **Input wedge after the demo sign-in.** In the tab where the demo sign-in was clicked, agent-browser's clicks stop reaching the page from the first click after sign-in. They still report `✓ Done`, but nothing happens: nav links don't change `location.hash`, `button[data-add]` "Add a sample" adds no row and test chips don't tick. `fill`, `eval` and `open` keep working, so a filled description is no proof that clicks land. Visiting `#/submit` is not the trigger; the wedge shows up without it. Right after signing in, open a fresh tab with `agent-browser tab new "$B/portal/#/"` and drive everything there; the portal session carries over, and clicks in the new tab keep working through `#/submit` and after it. Check `agent-browser eval 'location.hash'` after each navigation click. The cause is not known.
- **Hypothesis.** **Stale script after a `public/portal/` change.** Once, a reused tab still showed the old double sign-in after the fix while a new tab showed the fix; a cached `portal.js` module is the suspected cause, not proven, and a later review could not reproduce it. Open a new tab with a cache-busting query, such as `agent-browser tab new "$B/portal/?v=$RANDOM#/"`.
